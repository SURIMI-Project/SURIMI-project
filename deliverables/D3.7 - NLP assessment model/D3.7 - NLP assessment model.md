The NLP assessment model surfaced as the **SURIMI data server**, under the tag SURIMI-data-mcp. This assessment model exposes the SURIMI data lake and its toolboxes, data quality and definitions, as well as general terminology and related items, that can be accessed via natural language using an EDITO-hosted open weight large language model, called Muse-Glimmer-30B from Red Hat.

*Figure 1. The NLP assessment model (dark) in the SURIMI framework. It answers from the SURIMI data lake, on the input side of the model ensemble; its sibling, the NLP policy model (D3.9), answers from what the models produce.*

While the main deliverable of this SURIMI-data-mcp is limited to exposing and serving the tools and the data lake, it is also baked in inside a proper wiring UI called SURIMI-vllm-ui. It is a chat interface built on open-webui, with the language model served by SURIMI-vllm on the EDITO GPU node (section 3.2). Thus an EDITO user can run and deploy this ready to use setup via their browser, without installing anything. The two SURIMI servers, the chat interface and the language model all run as services of the SURIMI project on the EDITO Datalab and are launched from the EDITO service catalogue.

SURIMI-data-mcp is a Model Context Protocol server, so it is not tied to EDITO: it can also be wired into a frontier model such as Claude.ai or ChatGPT, into Mistral Chat, or into a terminal client such as opencode.[^1]

On 60 questions from ten domain experts, three runs of the deployed chat answered 28 to 32 of the 45 that SURIMI's data supports, 16 to 19 of them in full, and declined 14 of the 15 it does not support (section 6.3).

The sibling deliverable, SURIMI-model-mcp (D3.9), serves the simulation output and the gridded forcing data for the model GUI side, and the language model picks the server based on the question. Integration into the model GUI itself, due in April 2027, is outside this deliverable.

## 1. Model purpose

The NLP assessment model lets a user ask about SURIMI's data in plain language and get an answer that is easy to follow without a detailed understanding of the quantitative models behind it. It works outside the model loop, as a helper that summarises and explains tables, charts and indicators for users who are less used to quantitative data, and D3.7 applies it to the SURIMI data lake.

The model sits on the data GUI side of the platform and assesses information from the whole data lake, which is wider than simulation output alone. It explains what a user is looking at (indicators, units, confidence intervals, coverage and sources), retrieves and explains the metadata of a dataset, discovers and recommends datasets for a given question, produces charts through a pre-built tool catalogue and never by writing code, and answers "what can this tool do?" for a new user. It does not run simulations, does not generate or execute scripts, and does not read user-space data or the user's screen.

For this reason the model is built as a tool server and not as a trained network. The AI-based part is the language model that drives the tools, and it is replaceable, as the server has been driven by Muse-Glimmer-30B, Qwen3-Coder-30B and Claude Sonnet during development.

## 2. Process overview and scheduling diagram

Every question is handled as one conversation turn. The chat interface passes the question and the server's tool descriptions to the language model, runs each tool call the model asks for against the server, and hands the result back to the model until it answers, as the diagram below shows.

```mermaid
sequenceDiagram
    participant User as User
    participant UI as Chat UI and tool loop (SURIMI-vllm-ui)
    participant LLM as Language model (SURIMI-vllm)
    participant DATA as NLP assessment model (SURIMI-data-mcp)
    participant STORE as Trino / DuckDB cube / S3

    User ->> UI: question in natural language
    loop until the model answers (at most 12 rounds)
        UI ->> LLM: conversation + tool descriptions
        LLM -->> UI: tool call, e.g. list_datasets / aggregate / explain_indicator
        UI ->> DATA: the same call, over MCP
        opt query tools
            DATA ->> STORE: SQL over the data lake
            STORE -->> DATA: rows
        end
        DATA -->> UI: finding + rows + chart spec + signed receipt
    end
    LLM -->> UI: answer with source and [receipt:id]
    UI -->> User: answer and chart
    opt the user checks a figure
        User ->> UI: "Recompute on server"
        UI ->> DATA: receipt to /audit/verify
        DATA -->> UI: recomputed figure
        UI -->> User: claimed vs recomputed
    end
```

## 5. Outputs

### 5.1 Finding envelope

Every server-executed skill returns a single response that holds a plain-language finding, the rows it rests on, a chart specification, the parameters that were used, and a receipt, which the chat interface renders as a chart while any other client is free to render its own.

### 5.2 Receipt

Every analytical figure carries an HMAC-signed receipt recording the query that produced it and the data it read. The `verify` tool, or the "Recompute on server" button in the chat interface, re-runs that query against the live data and reports the claimed and the recomputed figure side by side, while the "Verify receipt" button checks only the signature.

### 5.3 Refusal

Where the served data does not support a question, the capability registry states which of three cases applies: the data is not served here, no mechanism exists, or it was never collected. The answer says so and, where it applies, where the data does live.

### 5.4 Audit page

The server publishes all 60 evaluation questions at `/audit/experts`, showing for each the model's answer, the answer the data supports, the source files and the commands that reproduce its figures, and every released version keeps its own URL.

## 6. Benchmark accuracy

A language model can misread a question, miss what the data holds, or state a figure the data does not support. This section reports how often that happens with the deployed setup, so a reader knows what to expect from it and where it falls short. It starts with the prompts that steer the model, because they decide what the model is asked to do. In this model the prompts are of three kinds: the server-side prompts fixed in each analytical skill, the tool descriptions the language model reads before each call, and the system prompt of the ready to use wiring. Together they aim for one behaviour: the model explains what SURIMI's data can support, refuses what it cannot, and never presents an unsupported figure as fact.

### 6.1 Objectives for each prompt

The data server carries five server-executed skills whose prompts are fixed in `skills.py`, so that their wording cannot drift between chat clients:

| Skill | Objective |
| --- | --- |
| `analyze_trend` | State the direction and size of change of one metric over time, with the coverage it rests on. |
| `compare_countries` | Compare one metric across countries for the same period, resolving the country column per dataset. |
| `breakdown` | Split one metric by a grouping column and rank the parts. |
| `explain_provenance` | Say where a dataset came from, who collected it and how it was processed, as one lineage sentence per source. |
| `generate_report` | Assemble the findings of the skills above into one dated report with its receipts. |

The tool descriptions steer discovery, in that `list_datasets` returns each table's exact name to be copied verbatim, `list_columns` states that it shows the commonly used columns and that a table has more, and `describe_data_capabilities` states which classes of question the server does not serve, so that the model can refuse with the reason.

The system prompt of the wiring, `SYSTEM_PROMPT` in `openwebui_functions/surimi_pipe.py` of SURIMI-vllm-ui, consists of the following blocks:

| Prompt block | Objective |
| --- | --- |
| Register | Write for policy-makers and stakeholders, not only scientists. Lead with the direct answer in everyday words. Define each technical term at first use. Keep ports, protocols and class names out of the answer. |
| Gridded ocean data | Find the NetCDF file, pick the variable, and resolve a named region with `model_list_regions`, never by guessing it. Then call the analytic tool: top regions, time series, period comparison or trend. |
| Tabular fisheries, economics and employment | Prefer the guided skills for a whole analysis: `analyze_trend` for change over time, `compare_countries` across countries, `generate_report` for a report, `explain_provenance` for sources and method. Otherwise query with SQL. |
| Rules | Never invent a path, variable, region, column or number. Write species, gear and country codes verbatim unless a tool returned the name. Cite each figure with its receipt id. Say plainly when a tool reports no data. |
| Informal-name routing | Map the user's everyday words to the dataset that answers them, for example fleet capacity to the AER capacity table and subsidies to the OECD support view. |
| Data catalogue | List the only tables and columns that exist, each with its real year coverage, so that a sum without a year filter is recognised as adding years together. |

### 6.2 How the model is evaluated

The model is evaluated in two ways. The first is the server's own behavioural benchmark of 105 cases in `benchmark/` of SURIMI-data-mcp, each with a grounding command that recomputes the expected figure from the data and scored by a deterministic numeric grader, which runs against every release.

The second is an expert evaluation. Eleven domain experts reviewed the assistant between August and September 2026 and filed fifteen survey submissions, ten of them contributed questions, and these were recorded as asked and then adjudicated into four classes according to whether SURIMI holds the data and whether a served tool reaches it. The expected answer for each question was established independently of the model: three agents searched the raw data lake, a judge reconciled their findings and an auditor checked the judge. On 30 September 2026 twenty of the answers were re-derived figure by figure by three independent reviewers. Each question was then put to the deployed stack on its own, with no prior conversation, and the reply was graded three times by a language-model judge against the expected answer, with the majority verdict counting. The three verdicts agree on 50 to 59 of the 60 answers in each run. An answer counts as correct when it delivers what the question asks with the right figures, and as partial when a central part of the question goes unanswered. A refusal that surrounds its refusal with context, a restatement of the question's premise, a listing of tables where an analysis was asked, and a significance claim that ignores autocorrelation in the data are not credited as answers.

### 6.3 Result

The evaluation of 1 October 2026 was run three times against data-mcp 1.2.37 and 1.2.38 and model-mcp 1.2.11, with Muse-Glimmer-30B (W4A16) through the chat interface in the configuration released as vllm-ui 0.2.79, which runs each model call with a budget of 6000 tokens as the evaluation did. The audit page of this evaluation is `/audit/experts/v_dm1.2.39_mm1.2.11` on the data server. As the question set is not split by server, the figures below are for the two servers together. The reference column is one run of Muse-Glimmer-30B on both servers through opencode, judged like the chat runs.

*Figure 3. The 45 expert questions SURIMI's data can answer, 1 October 2026. The top three bars are three runs of the deployed setup, Muse-Glimmer-30B through the EDITO chat (vllm-ui 0.2.79). The bottom bar is the opencode reference.*

The three runs of the chat differ by up to four answers on the 45, and that is the variation of the system, not the effect of a change. Twenty-seven questions were answered in all three runs, 11 in none and 7 in one or two. Fourteen were answered in full in all three runs and 20 in at least one.

Two changes were measured against the previous chat in the same judging batch, on the 44 answerable questions all three runs completed. Listing every table the data server holds in the chat's system prompt raised the count answered from 26 to 31 (16 to 18 in full) and removed the one wrong answer; it was released as vllm-ui 0.2.79. Removing the 12-round limit and the forced refusal raised it to 32 but lowered the full answers to 13, and it was not released.

### 6.4 Known limits

The largest limitation is the 13 to 16 refusals, where the data is served and the answer reproducible while the language model does not retrieve it. The opencode reference refused 7 of the 45 in a single run, a gap larger than the chat's own variation of up to four answers, so most of it lies in how the chat interface drives the model. The chat also stops a turn after 12 rounds of tool calls and then asks the model to answer from what it has.

From 22 to 29 September 2026 the chat interface did not connect to the model server (D3.9). A change to its connection code rejected an argument that the model server's transport passes, and the interface answered with the data server's tools alone. vllm-ui 0.2.77 corrected it on 29 September, and the figures in section 6.3 are measured after it.

An earlier evaluation on 29 September reported 39 of 50 answered and 24 in full. It used a more lenient rubric and expected answers that in part described what the tools return, and it is superseded by the figures above.
