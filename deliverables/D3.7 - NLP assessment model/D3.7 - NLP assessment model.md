SURIMI-data-mcp is the natural language processing (NLP) assessment model of the SURIMI toolbox. It lets users ask questions about the SURIMI data lake in their own words, for example which data exists, what a table or an indicator means, how complete the data is, where specific data can be found and what it shows. It can also produce plots from the data.

A large language model (LLM) reads the user's question and calls the server's tools, and the tools query the data to produce the answer. Users work through the SURIMI chat (SURIMI-vllm-ui). Under each answer, the chat states how the number was obtained and from which table, and the user can open the SQL query the server ran. The server runs on the Kubernetes platform of the European Digital Twin of the Ocean (EDITO) and is used with Muse-Glimmer-30B, an open-weight language model from Red Hat. This document describes the purpose of the model (§1), how it answers a question (§2), its inputs (§3) and outputs (§4), and how accurately it answered 60 questions collected from ten domain experts during the project (§5).

A second NLP model, SURIMI-model-mcp (D3.9), complements it by answering questions about the SURIMI simulation runs and about gridded ocean and climate data (Figure 1). The chat is connected to both servers, and the language model served by SURIMI-vllm decides which one to call.

## 1. Model purpose

SURIMI-data-mcp is the NLP assessment model of SURIMI. Its purpose is to make the data behind the SURIMI models usable by people who do not work with it every day, such as fisheries managers or policy officers. It is a server that holds the data catalogue and the tools to look up, compute and explain the data, and it is the main deliverable of D3.7. Users do not talk to the server directly. They type their question in the chat (SURIMI-vllm-ui), and an LLM served by SURIMI-vllm reads the question, calls the server's tools and writes the answer. The chat and the LLM are not part of the deliverable, but they let people use the server in their own language. Users can ask about the SURIMI data lake, its metadata, or how the SURIMI systems and modelling infrastructure are built. SURIMI-data-mcp works outside the simulation loop and takes no part in a SURIMI experiment. Its tools summarise and explain the tables, indicators and charts of the data lake.

In the data GUI, the part of the SURIMI platform for exploring the data lake, users can ask which data exists on a topic and which dataset fits their needs. With the server's tools, the LLM explains what a table, indicator, code, unit or confidence interval means, where the data came from and how complete it is. The numbers themselves, whether shown as a single value, a table or a chart, are calculated by the server and not by the LLM. The `describe_data_capabilities` tool lets the LLM tell a new user what the system can and cannot answer, and the chat draws charts from the data the server returns. Neither of the two NLP models runs simulations or reads the user's own data or screen.

For example, when asked how much Spain landed in 2022, the language model first looks up which dataset holds landings data. It then calls the server's `aggregate` tool, which sums Spain's 2022 landings in the EU catch table (by country, quarter, gear and species), and replies with the total of 749,178 tonnes. Below the answer, the chat shows how the number was calculated: "Sum of `total_live_weight_landed` in ‘EU DCF FDI Catches by Country, Quarter, Gear and Species’, where `country` is `'Spain'` and `year` is 2022."

A language model that answers from memory alone can give numbers that no data supports ([Ji et al., 2023](https://doi.org/10.1145/3571730)). SURIMI-data-mcp avoids this because it is a server rather than a trained model, and every number in an answer is looked up in the data by one of its tools. The language model does not hold the data. It picks a tool, the server runs it on the data, and the model writes its answer from the result. This design builds on earlier work on tool-using language models, such as [Yao et al. (2022)](https://doi.org/10.48550/arXiv.2210.03629) and [Schick et al. (2023)](https://doi.org/10.48550/arXiv.2302.04761). Definitions are taken from the public SURIMI documentation, using the retrieval approach of [Lewis et al. (2020)](https://doi.org/10.48550/arXiv.2005.11401). Because the data and the rules are kept in the server, the language model can be replaced. During development we tested the server with Muse-Glimmer-30B, Qwen3-Coder-30B and Claude Sonnet.

As explained above, the NLP assessment model is used through three closely linked parts, and only SURIMI-data-mcp is the deliverable:

- **SURIMI-data-mcp** ([SURIMI-Project/SURIMI-data-mcp](https://github.com/SURIMI-Project/SURIMI-data-mcp)), the data server and the deliverable of D3.7. It holds the catalogue of 28 datasets and offers 20 tools over the Model Context Protocol (MCP; [Anthropic, 2025](https://modelcontextprotocol.io/specification/2025-06-18)), an open standard that lets a language model call external tools. It is written in Python with FastMCP, stores its tables in PostgreSQL and computes totals, averages and counts in DuckDB ([Raasveldt and Mühleisen, 2019](https://doi.org/10.1145/3299869.3320212)).

- **SURIMI-vllm-ui** ([SURIMI-Project/SURIMI-vllm-ui](https://github.com/SURIMI-Project/SURIMI-vllm-ui)), the chat on EDITO (supporting part). It is a standard Open WebUI deployment with a SURIMI assistant ([`surimi_pipe.py`](https://github.com/SURIMI-Project/SURIMI-vllm-ui/blob/master/openwebui_functions/surimi_pipe.py)) that sends the question to the language model, runs the tools the model requests on both SURIMI servers, and shows under each answer how the numbers were calculated.

- **SURIMI-vllm** ([SURIMI-Project/SURIMI-vllm](https://github.com/SURIMI-Project/SURIMI-vllm)), the language model service (supporting part). It runs the model on the EDITO graphics processing unit (GPU) node with vLLM ([Kwon et al., 2023](https://doi.org/10.1145/3600006.3613165)).

The chat and the language model service are not part of the deliverable. They are needed, however, so that people can use SURIMI-data-mcp in their own language from a browser on EDITO, without installing anything.

Technical details are in two documents in the repository. The [architecture document](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/data_mcp_architecture.md) describes how the server handles a request, and the [tool reference](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/docs/tools.md) lists each tool and what it does. The [README](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/README.md) explains how to connect other MCP clients, such as Claude.ai, ChatGPT, Mistral Chat and opencode. The [workshop cheat sheet](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/docs/workshop-cheatsheet.md) shows how to connect Claude Desktop.

## 2. Process overview and scheduling diagrams

The sequence diagram below shows how a question is answered. The chat sends the question to the language model along with descriptions of the server's tools. The model then either answers directly or asks for a tool call, which the chat runs on the server before passing the result back to the model. This loop continues until the model has its answer, for at most 12 rounds by default. The architecture document follows a single `aggregate` call through the server step by step ([request flow](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/data_mcp_architecture.md#request-flow-for-aggregate)).

```mermaid
sequenceDiagram
    participant User as User
    participant UI as Chat UI and tool loop (SURIMI-vllm-ui)
    participant LLM as Language model (SURIMI-vllm)
    participant DATA as NLP assessment model (SURIMI-data-mcp)
    participant STORE as Trino / DuckDB cube / S3

    User ->> UI: question in natural language
    loop until the model answers (at most 12 rounds)
        UI ->> LLM: conversation + tool descriptions
        LLM -->> UI: tool call, e.g. list_datasets / aggregate / explain_indicator
        UI ->> DATA: the same call, over MCP
        opt query tools
            DATA ->> STORE: SQL over the data lake
            STORE -->> DATA: rows
        end
        DATA -->> UI: finding + rows + chart spec + how it was calculated
    end
    LLM -->> UI: answer with source
    UI -->> User: answer, chart and how each figure was calculated
    opt the user checks a figure
        User ->> UI: "SURIMI Re-run on live data"
        UI ->> DATA: the figure's record to /audit/verify
        DATA -->> UI: recomputed figure
        UI -->> User: claimed vs recomputed
    end
```

## 4. Outputs

### 4.1 Analyses run on the server

Five of the tools run a complete analysis on the server ([`engine/skills.py`](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/surimi_data_mcp/engine/skills.py)): `analyze_trend`, `compare_countries`, `breakdown`, `explain_provenance` and `generate_report`. Each one returns a short written finding together with the underlying rows, a chart specification, the settings used and the calculation record for each number (§4.2). The chat turns the specification into a chart, and other MCP clients can render it in their own way.

### 4.2 How each number was calculated

Each number that the server calculates with a query comes with a short record of how it was obtained ([`provenance/`](https://github.com/SURIMI-Project/SURIMI-data-mcp/tree/master/surimi_data_mcp/provenance)). The record contains a sentence describing what the query did and on which table, the SQL query with its values filled in, and the source file in the data lake where there is one. The server writes this sentence from the query it actually ran, so the description cannot be invented by the language model. Under each answer the chat shows the sentence and the source, with a link to the server's audit page ([`static/audit.html`](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/static/audit.html)). The user can also open the SQL query or run it again on the current data. The record is also signed (HMAC; [Krawczyk et al., 1997](https://doi.org/10.17487/RFC2104)), similar to the tool receipts described by [Basu (2026)](https://doi.org/10.48550/arXiv.2603.10060).

### 4.3 Refusal

If the data on the server cannot answer a question, the model says so and explains why. The server keeps a list of questions it cannot answer ([`sources.py`](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/surimi_data_mcp/sources.py), [`capabilities.py`](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/surimi_data_mcp/capabilities.py)), sorted into three cases: the data exists but is not on this server, no SURIMI model computes it, or it was never collected. If the data is available elsewhere, the answer points to it.

### 4.4 Audit page

The evaluation in §5 is published on the server's audit page, `/audit/experts`. For each of the 60 questions, the page shows the model's answer, the answer supported by the data, the source files and the commands that reproduce the numbers ([`audit-repro/`](https://github.com/SURIMI-Project/SURIMI-data-mcp/tree/master/audit-repro)). Each released version has its own address.

## 5. Benchmark accuracy

Even with tools, a language model can misread a question, miss data that the server holds, or give a number that no tool returned. Three sets of prompts are used to reduce these errors: the prompts of the five analyses, the tool descriptions the language model reads, and the system prompt of the chat. Together they tell the model to explain what SURIMI's data supports, to decline questions it cannot answer, and not to present unsupported numbers as fact.

### 5.1 Objectives for each prompt

The prompts of the five analyses are fixed in [`engine/skills.py`](https://github.com/SURIMI-Project/SURIMI-data-mcp/blob/master/surimi_data_mcp/engine/skills.py), so they stay the same whichever MCP client is used:

| Tool | Objective |
| --- | --- |
| `analyze_trend` | Report the direction and size of change of one metric over time, and the data coverage behind it. |
| `compare_countries` | Compare one metric across countries for the same period, using the correct country column for each dataset. |
| `breakdown` | Split one metric by a grouping column and rank the parts. |
| `explain_provenance` | Describe where a dataset came from, who collected it and how it was processed, in one sentence per source. |
| `generate_report` | Combine the results of the analyses above into one dated report, with the query behind each number. |

The tool descriptions mostly help the model find the right data. `list_datasets` returns the exact name of each table. `list_columns` returns the columns of a table as stored in the database and flags tables that keep each year in a separate column. `describe_data_capabilities` lists the kinds of question the server cannot answer, so the model can decline and give the reason.

The chat's system prompt (`SYSTEM_PROMPT` in [`surimi_pipe.py`](https://github.com/SURIMI-Project/SURIMI-vllm-ui/blob/master/openwebui_functions/surimi_pipe.py)) has six blocks:

| Prompt block | Objective |
| --- | --- |
| Register | Write for policy-makers and stakeholders, not only scientists. Give the direct answer first, in everyday language. Define each technical term at first use. Leave out ports, protocols and class names. |
| Gridded ocean data | Find the NetCDF file, choose the variable, and look up a named region with `model_list_regions` instead of guessing it. Then call the matching analysis tool: top regions, time series, period comparison or trend. |
| Tabular fisheries, economics and employment | For a full analysis, use the guided tools first: `analyze_trend` for change over time, `compare_countries` across countries, `generate_report` for a report, `explain_provenance` for sources and method. Otherwise query with SQL. |
| Rules | Never invent a path, variable, region, column or number. Write species, gear and country codes verbatim unless a tool returned the name. Give each number without its calculation record, since the chat adds the record under the answer. Say plainly when a tool reports no data. |
| Informal-name routing | Link the user's everyday terms to the right dataset, for example fleet capacity to the AER capacity table and subsidies to the OECD support view. |
| Data catalogue | List all tables and columns that exist, with the years each one covers, so the model can see when a sum without a year filter adds several years together. |

### 5.2 How the model is evaluated

The model is evaluated in two ways. The first is a benchmark of 105 test cases, kept in the project's internal repository, that runs against every release of the server. For each case, a script calculates the expected number directly from the data, and a grader compares it with the number in the model's answer. No language model is involved in this step.

For the second, eleven domain experts, with backgrounds ranging from stock assessment to marine policy, reviewed the assistant in August and September 2026. Ten of them contributed 60 questions of the kind they would ask in their work (Table 4). Language-model agents worked out the expected answer to each question from the raw data lake, without using the SURIMI servers, and on 30 September 2026 three independent reviewers checked twenty of these answers number by number. Of the 60 questions, 45 can be answered from the data and 15 should be declined. Each question was put to the chat separately, and a language-model judge ([Zheng et al., 2023](https://doi.org/10.48550/arXiv.2306.05685)) graded each reply against the expected answer as correct, partial, refused or wrong. All questions, answers and verdicts are on the audit page (§4.4).

### 5.3 Result

The evaluation was run three times on 1 October 2026, with Muse-Glimmer-30B answering through the chat and a limit of 6000 tokens per reply (versions in Table 2). Because the questions are not split by server, the results below cover both servers together. For reference, the same language model also answered the questions once through opencode, a terminal client, and was judged in the same way. The audit page for this evaluation is `/audit/experts/v_dm1.2.39_mm1.2.11` on the data server.

| Wrong | 0 to 1 | 2 |

*Figure 3. The 45 expert questions SURIMI's data can answer, 1 October 2026. The top three bars are the three runs of Muse-Glimmer-30B through the chat on EDITO, and the bottom bar is the opencode reference.*

The three runs differ by at most four answers (Figure 3), and the differences come from a small number of questions. Of the 45 answerable questions, 27 were answered in every run, 11 in none, and the remaining 7 in one or two runs. Fourteen questions were fully answered every time, and 20 at least once.

We also tested two changes to the chat against the previous version, judging all answers together, on the 44 answerable questions that every run completed. Adding a list of all data server tables to the system prompt increased the number of answered questions from 26 to 31 and the number of full answers from 16 to 18, and it removed the one wrong answer. This change was released. Removing the 12-round limit on tool calls, together with the refusal the chat forces when the limit is reached, increased the answered questions to 32 but reduced the full answers to 13, so this change was not released.

### 5.4 Known limits

The main weakness is that the chat is too cautious. In 13 to 16 of the 45 answerable questions, the data was on the server and the answer could have been computed, but the language model declined without looking it up. Through opencode, the same model declined only 7. This gap is larger than the variation between the chat's own runs, which suggests that most of it comes from how the chat drives the model rather than from the data or the tools. In addition, the chat stops after 12 rounds of tool calls and asks the model to answer with what it has.
