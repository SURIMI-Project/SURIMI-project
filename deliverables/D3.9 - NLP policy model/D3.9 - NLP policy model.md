SURIMI-model-mcp is the natural language processing (NLP) policy model of the SURIMI toolbox. Its job is to help people make sense of what the SURIMI simulations found. A policy officer can ask, for instance, whether a stock is overfished in the latest experiment, or what a run holds for a given stock. They get a plain answer that points back to the run it came from.

Behind the chat, a large language model (LLM) works out what the user is asking and chooses the server's tools, which the chat then runs. The tools read the numbers, not the LLM. The runs come from the CMSY++, market, Controller, Fisheries Authority and Output Creator models, which store their results on the European Digital Twin of the Ocean (EDITO). Users reach it through the SURIMI chat (SURIMI-vllm-ui), with the same language model as D3.7: Muse-Glimmer-30B, an open-weight LLM from Red Hat. What it can answer is limited by what each run contains and by the server's access to EDITO storage, which lapses a day after launch (§5.4).

A second NLP model, SURIMI-data-mcp (D3.7), complements it by answering questions about the SURIMI data lake, the data the models start from (Figure 1).

![Data flow](data_flow_NLP_policy.png)
 <em>Figure 1. Position of the NLP policy model (dark) within the SURIMI framework. It reads the NetCDF and run files that the SURIMI models write to EDITO storage (S3), while the NLP assessment model (D3.7) reads the raw data and metadata on EDITO data storage (S3) that the SURIMI models use.</em>

SURIMI-model-mcp does not run simulations itself. A SURIMI experiment takes one to two days, so the model works with runs that modellers have already completed.

## 1. Model purpose

SURIMI-model-mcp is the NLP policy model of SURIMI. Its purpose is to explain what the simulations say about a policy choice, so that people who do not run the models themselves can see why one policy performs better than another. It is a server that holds the tools to find, read and explain the simulation results, and it is the main deliverable of D3.9. Most users do not talk to the server directly. They type their question in the chat (SURIMI-vllm-ui), and an LLM served by SURIMI-vllm reads the question and chooses the server's tools. The chat runs the tools and passes the results back, and the LLM writes the answer. In SURIMI, a policy choice is a management strategy whose effect the simulations compare. At present this is a harvest control rule that sets a total allowable catch for each species that has a rule, at the start of each regulatory year. Two models make up the policy layer of the ensemble. The management strategy evaluation (MSE) policy model (D3.8) sets these catch limits from harvest control rules while the simulation runs. This one works outside the simulation and explains its results afterwards.

Take the question of whether a stock is overfished in the latest experiment. The LLM first lists the runs and opens the experiment's output file. It then reads the stock's status with `model_run_stock_status`, which gives two ratios: the stock's biomass relative to the biomass at maximum sustainable yield (B/Bmsy), and its fishing pressure relative to the level at maximum sustainable yield (F/Fmsy). The answer names the run, the stock and the file, and points out that this file carries no uncertainty bounds. The server never changes a stored file and does not read data supplied by the user.

The stock results it reads come from CMSY++ (D3.6), which estimates biomass and fishing pressure relative to maximum sustainable yield from catch and, where available, an abundance index ([Froese et al., 2023](https://doi.org/10.3897/aiep.53.105910)). The gridded results are NetCDF files, which the server reads with xarray ([Hoyer and Hamman, 2017](https://doi.org/10.5334/jors.148)).

Only the model server, [SURIMI-model-mcp](https://github.com/SURIMI-Project/SURIMI-model-mcp), is the deliverable. It is a Python program built on FastMCP that reads its files directly from `project-surimi`, the project's bucket in the EDITO object storage, with no database in between. It offers 26 tools over MCP, the Model Context Protocol ([Anthropic, 2025](https://modelcontextprotocol.io/specification/2025-06-18)). The chat (SURIMI-vllm-ui) and the language model service (SURIMI-vllm) are shared with D3.7 and support the server, but they are not part of this deliverable.

### 2.1 The tools

SURIMI-model-mcp has 26 tools in five groups (Table 1). Seven read simulation runs, nine describe gridded files and four summarise them, five look up reference information, and one checks that the record of a gridded result has not changed.

*Table 1. The 26 tools by group.*

| Group | What they answer |
| --- | --- |
| Simulation | The runs that exist and what each is about, the files and metadata of one run, the status of a stock on the Kobe plot (B/Bmsy against F/Fmsy) and its trajectory, and the meaning of a CMSY++ field. |
| Gridded files and coverage | What a file holds, its regions and period, and whether two files align. |
| Gridded series | Series, trends, comparisons between periods and rankings of regions. |
| Reference | The structure of an ecosystem model file, the scenario contract, species and gear codes, and the questions the server can and cannot answer. |
| Verification | Checks that the record of a gridded result has not changed since the server produced it. |

## 3. Inputs

Apart from the user's question, the model reads only what is in the `project-surimi` bucket on EDITO: the simulation runs, the gridded files and the reference tables.

### 3.1 Simulation runs

Each model uploads its runs to a directory of its own, and a run is a subdirectory named by a UUID (the Fisheries Authority writes flat files prefixed by the UUID; Table 2). These runs are read by the seven simulation tools ([`simulations/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/simulations)). `model_list_simulations` gives a one-line summary of each run that has a parser (the stock, years and biomass type for a CMSY run), and `model_describe_simulation` lists the files and metadata of a single run. The stock tools then report a stock's status and its year-by-year trajectory, read either from a CMSY++ result table or from the run's NetCDF file. `model_explain_assessment_field` explains a fixed set of CMSY++ fields (`btype`, `force.cmsy`, Resilience, N bt, last B/Bmsy, last F/Fmsy and the year-indexed columns) and says so for any other, while `model_get_artifact` returns a text file from a run inline (cut at a size cap) and any binary file as a download link.

The Output Creator, the SURIMI component that writes an experiment's output file, stores the CMSY++ results as arrays inside the NetCDF file rather than as a result table. `model_run_stock_status` reads B/Bmsy and F/Fmsy for each stock. Without a stock name it gives every stock's position on the Kobe plot, which places a stock by B/Bmsy against F/Fmsy, in one year and the count per quadrant; for a named stock it adds the trajectory. The file has no uncertainty bounds and does not say which years are historical and which are simulated, and the tool states this in every answer. At the time of the evaluation the bucket held one such run, covering 47 western Mediterranean stocks up to 2013; by 9 October 2026 it held eight. The Fisheries Authority model had uploaded 35 harvest-control-rule runs at the time of the evaluation and 54 by 9 October 2026. These are served as files through `model_get_artifact`.

The Output Creator writes the output file once the experiment has ended, as a NetCDF4 file, together with the raw recording (`.bin`) of the experiment, under `output_creator/experiments/<id>/`. The file holds biomass on the model grid by species; gross catch and live and dead discards on the grid by species and fleet; and totals per species and per fleet. It also holds prices, sales value and sales quantity by market, and fishing activity by fleet. If the experiment includes stock assessments, the file also carries stock status and exploitation by year and species, which is what `model_run_stock_status` reads. The output file carries no value-chain results.

### 3.2 Gridded files and region masks

The files under `netcdf/` come from outside SURIMI: gridded data (today an EcoOcean/FishMIP biomass density file) and the region masks used to summarise them. The thirteen gridded tools never pass the grid cells to the LLM. The analytic ones return a summary over a named region, such as a series, a trend or a ranking of regions, and the others return file metadata ([`netcdf/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/netcdf)).

### 3.3 Reference and contract

The reference tools describe the structure of an EwE ecosystem model file and resolve species, gear and country codes and taxon names. They also return the SURIMI scenario contract, which lists markets, currencies and fleet segments, gives the number of species, and states the code standards and units; it is the northwestern_med contract. `describe_model_capabilities` states which kinds of question the server can and cannot answer ([`reference/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/reference)).

## 4. Outputs

### 4.1 Run discovery

`model_list_simulations` returns the runs in the bucket, newest first, optionally filtered by model, each with its model, run id, number of files, last-modified time and, where a parser exists, a one-line summary and the stock. If some objects could not be listed, it marks the list as partial.

### 4.2 Stock status and trajectory

`model_get_stock_status` and `model_get_stock_trajectory` return the status of a stock in a given run and phase (`historical` or `simulation`, Table 3) as B/Bmsy and F/Fmsy, together with their bounds and the estimator that produced them, and its trajectory over the years. They read the result exactly as the CMSY++ script wrote it (Table 3), and the answer names the file it came from. No CMSY++ result table that these tools accept is in the bucket yet, so today only `model_run_stock_status` (point values, no bounds) returns stock status.

*Table 3. How a stock result is read.*

| Setting | Value |
| --- | --- |
| Source | `CMSY_output_historical.csv` or `CMSY_output.csv` of a run, written by the CMSY service. A run with only the older `Out_..._id_file.csv` is refused by name. |
| Phase | Required argument, `historical` (assessed from observed catch and abundance) or `simulation` (assessed from ecosystem-model output); a run without that split is refused by file name. |
| Estimator | Reported per stock result, CMSY (catch only) or BSM (catch plus abundance index), decided by the rule in the CMSY++ script (BSM when an abundance index has at least 5 years); the tool cannot see whether `force.cmsy` was set. |
| Bounds | Every point estimate carries `lcl` and `ucl`, stated as the 2.5th and 97.5th percentile of the Markov chain Monte Carlo (MCMC) posterior and not as a confidence interval. |

### 4.3 Gridded summary and definitions

The gridded tools return a series, a trend, a comparison between two periods or a ranking of named regions. Each result names the file, the variable and the region mask it came from, where a region mask is the set of grid cells that make up a named region. When the user asks about an assessment field, a code or an element of the scenario contract, the model defines it from the CMSY++ input description and script, the code tables, or the scenario contract.

### 4.4 Refusal

When no run or file can answer the question, the server returns an error or a capability record naming what it cannot answer ([`sources.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/sources.py), [`capabilities.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/capabilities.py)), and the chat states what was looked for.

## 5. Benchmark accuracy

As in D3.7, the LLM can misread a question, miss a run the server holds, or give a number that no tool returned. Two sets of prompts are used to keep these errors down on this server: the tool descriptions that the LLM reads, and the system prompt of the chat. Together, they tell the model to answer only from SURIMI's runs and files and to decline anything they do not cover.

### 5.1 Objectives for each prompt

The prompts and what each one tells the model:

| Prompt | Objective |
| --- | --- |
| `model_list_simulations` description | Call first for any question about a run. Answer "which models have runs" from the scanned list, and "what is run X about" from the run's own summary and stock, without opening every run. Treat a null summary as unknown, never as a guess. Say when the listing is stale or partial. |
| `model_describe_simulation` description | Open one run only after the listing has picked it. Report the run's files and parsed metadata. |
| `model_get_stock_status` and `model_get_stock_trajectory` descriptions | Require the phase, historical or simulation, and refuse a run that has no such split, naming the file to fetch instead. For `model_get_stock_status` only: report every estimate with its bounds and say what the bounds are, and name the estimator, CMSY or BSM, and why. |
| `model_get_artifact` description | Fetch one file and say when the content is a cut prefix, never present it as the whole file. |
| `model_explain_assessment_field` description | Define a CMSY++ input or result column and how the script uses it, from the script's own documentation. |
| Gridded tool descriptions | Find the file, then choose the variable, then look up the exact region name in the mask, then call the matching analysis tool. Never guess a region name. Answer from the pre-aggregated summary. Prefer `model_trend` for "is it increasing" questions. |
| Chat system prompt, register and rules blocks | Give the answer first, in everyday language, for policy-makers and stakeholders. Define terms at first use. Never invent a file path, variable, region or column name, or number. Give every number with the dataset or report it came from and the period it covers. End every turn with a plain answer. |

### 5.2 How the model is evaluated

The server has its own benchmark of 54 test cases, built in the same way as that of D3.7. For each numeric turn, the expected number is the output of a grounding command run against the live server and recorded in the case, and a deterministic script compares it with the numbers in the model's answer. No language model is involved in this step. Turns the script cannot verify are left ungraded.

The server also takes part in the expert evaluation of D3.7 (§5.2). Three of the ten experts asked their questions from a policy position: a fisheries economist who also filled in the marine spatial planning form (E1), a marine science policy adviser (E2) and a science policy officer (E10). Between them they asked 19 of the 60 questions (Table 4).

### 5.4 Known limits

The model does not read the state of a running simulation, and it does not send regulations to the other models through the SURIMI protocol.

The CMSY++ runs in the bucket carry a single unlabelled result table and do not separate historical from simulated years. `model_get_stock_status` and `model_get_stock_trajectory` therefore decline them and name the file to fetch instead. The runs in the bucket are also filed by model and run identifier, not in a catalogue that records the region, climate scenario, policy measure and duration of each scenario. Runs filed in a new layout are found without a code change, but `model_list_simulations` has no field for region, climate scenario, policy measure or duration. The output of a run is on the model's own grid, 82 by 109 cells for the western Mediterranean. Because the server has no map of named regions on that grid, the tools cannot break a result down by area.

The server reads the bucket with a temporary storage token that the EDITO launcher issues for about 24 hours. At launch the server copies the runs, the NetCDF catalogue and the reference files onto its own volume. After the token expires, it keeps answering from that copy and marks its listings as stale. The language model is instructed to say so, and a file the server never copied is refused with a message that the server must be launched again on EDITO. Runs uploaded after the token has expired are not seen until the server is launched again, so a listing can be several days out of date.

The server reads the NetCDF files from the `netcdf/` folder of the `project-surimi` bucket, both set in its Helm chart. If the bucket is restructured, the server has to be reconfigured and launched again.

Many runs hold only the models' raw output. For such a run the server can say which variables, species, fleets and years the file holds and, where it carries stock assessments, report stock status by year. It cannot say what the simulation found about a policy or why.

With only 19 questions, the policy subset is small, and the number answered ranged from 5 to 7 between runs. All the questions that the chat declined but could have answered belong to the data server, not to this one.
