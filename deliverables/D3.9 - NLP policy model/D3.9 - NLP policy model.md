SURIMI-model-mcp is the natural language processing (NLP) policy model of the SURIMI toolbox. It lets a user ask in plain language what SURIMI's simulations found about a policy choice, such as a quota or a harvest control rule. It answers from the results the models have produced. These are the runs that the CMSY++, market, Controller and Fisheries Authority models upload to the project's storage on the European Digital Twin of the Ocean (EDITO), the stock assessments inside them, and the gridded ocean and climate files next to them. SURIMI-model-mcp answers from what the models produce, whereas SURIMI-data-mcp (D3.7) answers from the data the models start from; both are reached through the same chat and the same language model, Muse-Glimmer-30B. This document describes the model's purpose (§1), how the model answers a policy question (§2), and its inputs (§3) and outputs (§4), and reports how it answered the experts' policy questions (§5).

![Data flow](data_flow_NLP_policy.png)
 <em>Figure 1. Position of the NLP policy model (dark) within the SURIMI framework for the North-Western Mediterranean case study. It reads the simulation output the models produce; the NLP assessment model (D3.7) reads the data on EDITO that the models start from.</em>

The model does not run a simulation itself. A SURIMI experiment takes one to two days, so the model works over runs that modellers have already completed.

Of the 60 questions in the expert evaluation, 19 were asked from a policy position. In three runs, the chat answered 5 or 6 of them, declined the 9 that no SURIMI data or run can answer, and gave no wrong answer (§5.3).

Integration into the graphical user interface (GUI) of the models is planned for April 2027 and is not part of this deliverable.

## 1. Model purpose

As the NLP policy model of SURIMI, SURIMI-model-mcp's purpose is to explain what the simulations say about a policy choice, so that a user who does not run the models can follow why one policy performs better than another. In SURIMI a policy choice is a management strategy, such as a harvest control rule, a quota, a subsidy or an effort limit, tested by simulation across the model ensemble (D3.1 to D3.8). The policy layer of the ensemble has two models: the management strategy evaluation (MSE) policy model (D3.8), which sets regulations from harvest control rules inside the simulation, and this one, which works outside the simulation and explains its results afterwards.

The model sits on the model GUI side of the platform, where the what-if scenarios and policy measures are. A user can ask which simulations exist and what each one is about, compare scenarios, ask what a run found for a stock, and ask what the tool itself can do. Suppose a user asks whether a stock is overfished in the latest experiment. The language model lists the runs, opens the experiment's output file and calls `model_run_stock_status`, which reads the stock's biomass relative to the biomass at maximum sustainable yield (B/Bmsy) and its fishing pressure relative to the level at maximum sustainable yield (F/Fmsy). The answer names the run, the stock and the file, and says that this file carries no uncertainty bounds. Like D3.7, the model is a tool server driven by a replaceable language model, and it neither writes to storage nor reads data the user supplies.

The stock results it reads come from CMSY++ (D3.6), which estimates biomass and fishing pressure relative to maximum sustainable yield from catch and, where available, an abundance index ([Froese et al., 2017](https://doi.org/10.1111/faf.12190); [Froese et al., 2023](https://doi.org/10.3897/aiep.53.105910)). The gridded results are NetCDF files ([Rew and Davis, 1990](https://doi.org/10.1109/38.56302)), which the server reads with xarray ([Hoyer and Hamman, 2017](https://doi.org/10.5334/jors.148)).

The deliverable is the model server itself, [SURIMI-model-mcp](https://github.com/SURIMI-Project/SURIMI-model-mcp). The server is a Python program built on FastMCP. It reads its files from the project's bucket on EDITO without a database and offers 26 tools over MCP, the Model Context Protocol ([Anthropic, 2025](https://modelcontextprotocol.io/specification/2025-06-18)). It reads stock results the way the CMSY++ script writes them, with their bounds and estimator (§4.2), and returns the gridded files as small summaries over named regions, so that the language model never handles the raw grid (§4.3). Users reach it through the chat described in D3.7, which attaches it as its second tool server. Its technical documentation is its [architecture document](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/model_mcp_architecture.md), its [tool reference](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/docs/tools.md) and its [notes on behaviour](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/docs/behaviour.md).

## 3. Inputs

Apart from the user's question, the model reads only what is in the `project-surimi` bucket on EDITO: the simulation runs, the gridded files and the reference tables.

### 3.1 Simulation runs

Each model uploads its runs to its own directory, one subdirectory per scenario (Table 2). The seven simulation tools read them in turn. The listing gives a one-line summary and the assessed stock for each run; the description gives one run's files and metadata; and the stock tools give a stock's status and its trajectory by year, from a CMSY++ result table or from the run's NetCDF file. `model_explain_assessment_field` explains any input or result column of CMSY++. The readers are in [`simulations/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/simulations).

The Output Creator, the SURIMI component that writes an experiment's output file, stores the CMSY++ results as arrays inside the NetCDF file, not as a result table. `model_run_stock_status` reads B/Bmsy and F/Fmsy for each stock and, for a named stock, its trajectory and its position on the Kobe plot, which places a stock by B/Bmsy against F/Fmsy. The file carries no uncertainty bounds and does not mark which years are historical and which simulated, and the tool says so in every answer. The bucket held one such run, with 47 western Mediterranean stocks up to 2013, when the evaluation was run, and eight such runs on 12 October 2026. The harvest-control-rule runs of the Fisheries Authority model, 35 at the evaluation and 54 on 12 October 2026, are served as files through `model_get_artifact`.

The output file of an experiment is written by the Output Creator after the experiment ends, as one NetCDF4 file under `output_creator/experiments/<id>/`. It holds biomass, gross catch and live and dead discards on the model grid by species and fleet, with their totals per species and fleet. It also holds prices, sales value and sales quantity by market, and fishing activity by fleet. When the experiment includes stock assessments it adds stock status and exploitation by year and species, which `model_run_stock_status` reads. The value chain model is not finished, so no output file carries value-chain results yet.

### 3.2 Gridded forcing and observations

The files under `netcdf/` are external datasets of ocean and climate forcing and observations. The thirteen gridded tools never pass the grid itself to the language model. They return a summary over a named region instead, such as a series, a trend or a ranking of regions, small enough for the model to read whole ([`netcdf/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/netcdf)).

### 3.3 Reference and contract

The reference tools name the ecosystem model behind a run, return the SURIMI scenario contract, and resolve species and gear codes. `describe_model_capabilities` states which kinds of question the server can answer and which it cannot ([`reference/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/reference)).

## 4. Outputs

### 4.1 Run discovery

The listing returns the runs that bear on the question, each with its model, scenario, stock and year range. It is marked stale when the bucket cannot be reached and the server repeats its last good listing, and partial when some objects could not be listed (Table 2).

### 4.2 Stock status and trajectory

`model_get_stock_status` and `model_get_stock_trajectory` return the status of a stock in a given run and phase as B/Bmsy and F/Fmsy, with their bounds and the estimator that produced them, and its trajectory over the years. They read a result the way the CMSY++ script wrote it (Table 3), and the answer names the file.

*Table 3. How a stock result is read.*

| Setting | Value |
| --- | --- |
| Source | the CMSY++ result table of a run (`Out_..._id_file.csv`) |
| Phase | required argument, `historical` (assessed from observed catch and abundance) or `simulation` (assessed from ecosystem-model output); a run without that split is refused by file name |
| Estimator | reported per run, CMSY (catch only) or BSM (catch plus abundance index), decided by the same rule the CMSY++ script uses |
| Bounds | every point estimate carries `lcl` and `ucl`, stated as the 2.5th and 97.5th percentile of the Markov chain Monte Carlo (MCMC) posterior and not as a confidence interval |

### 4.3 Gridded summary and definitions

The gridded tools return a series, a trend, a comparison of two periods or a ranking over named regions, with the file, variable and region mask it came from. When the user names an assessment field, a code or an element of the scenario contract, the model defines it from the CMSY++ documentation, the SURIMI protocol or the reference tables.

### 4.4 Record and refusal

Five gridded tools (`model_validate_alignment`, `model_top_regions`, `model_time_series`, `model_compare_periods` and `model_trend`) return a record of the file, mask and parameters they used. The record is signed with a key that both servers and the chat share, as a keyed hash (HMAC; [Krawczyk et al., 1997](https://doi.org/10.17487/RFC2104); [`provenance/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/provenance)), and `model_verify` confirms that it has not changed. Results read from runs are not signed; they name the run, stock, phase and file they came from instead. Because the server reads files and not a database, there is no query to run again as in D3.7. When no run or file can answer the question, the server's list of the questions it cannot answer says so ([`sources.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/sources.py), [`capabilities.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/capabilities.py)), and the answer states what was looked for.

## 5. Benchmark accuracy

On this server two kinds of prompt steer the language model, the tool descriptions and the chat's system prompt, so that it answers only from SURIMI's runs and files and declines what they do not cover.

### 5.1 Objectives for each prompt

Each prompt that steers the model on this server has one objective:

| Prompt | Objective |
| --- | --- |
| `model_list_simulations` description | Call first for any question about a run. Answer "which models have runs" from the scanned list, and "what is run X about" from the run's own summary and stock, without opening every run. Treat a null summary as unknown, never as a guess. Say when the listing is stale or partial. |
| `model_describe_simulation` description | Open one run only after the listing has picked it. Report artifacts and parsed metadata. |
| `model_get_stock_status` and `model_get_stock_trajectory` descriptions | Require the phase, historical or simulation, and refuse a run that has no such split, naming the file to fetch instead. Report every estimate with its bounds and say what the bounds are. Name the estimator, CMSY or BSM, and why. |
| `model_get_artifact` description | Fetch one file and say when the content is a cut prefix, never present it as the whole file. |
| `model_explain_assessment_field` description | Define a CMSY++ input or result column and how the script uses it, from the script's own documentation. |
| Gridded tool descriptions | Find the file, then the variable, then the exact region name from the mask, then call one analytic tool. Never guess a region name. Answer from the pre-aggregated summary. Prefer `model_trend` for "is it increasing" questions. |
| System prompt of the wiring, gridded workflow block | The same four-step order, stated once for every client that uses the shared prompt. |
| System prompt of the wiring, register and rules blocks | Lead with the answer in everyday words for policy-makers and stakeholders. Define terms at first use. Never invent a run, stock, file or number. State every figure plainly, naming the run, stock, phase and file. End every turn with a plain answer. |

### 5.2 How the model is evaluated

The server has its own benchmark of 33 test cases, built like that of D3.7 and run against every release: a command computes each expected figure directly from the files, and the same grader compares it with the model's answer.

It also takes part in the expert evaluation of D3.7 (§5.2). Three of the ten experts asked from a policy position: a fisheries economist who also filled in the marine spatial planning form (E1), a marine science policy adviser (E2) and a science policy officer (E10). Together they asked 19 of the 60 questions (Table 4).

### 5.4 Known limits

The model does not read the state of a simulated fishery and does not emit regulations through the SURIMI protocol.

The runs observed live carry one unlabelled CMSY++ result table and no historical or simulation split, so `model_get_stock_status` and `model_get_stock_trajectory` refuse them by name. The output runs are now read from their NetCDF instead (§3.1). The bucket also holds runs filed by model and scenario directory, not a catalogue of scenarios that records a region, a climate scenario, a policy measure and a duration for each. When runs arrive with that information, the listing will use it without a change to the code. The output run is on the model's own grid, 82 by 109 cells for the western Mediterranean, and no region mask on that grid is served, so a question about which areas a result applies to cannot be split by area with the tools.

With 19 questions, the policy subset is small, and the number answered moved by one between runs. Every question the chat declined although it could have been answered is a question for the data server, not for this one.
