The NLP policy model is delivered as the SURIMI model server, SURIMI-model-mcp. ## 1. Model purpose

The NLP policy model explains in plain language what SURIMI's simulations found about a policy choice, so that users without a detailed understanding of the quantitative models can follow why a policy performs as it does. The policy layer of the SURIMI ensemble has two component models: the MSE policy model (D3.8), which computes regulations from harvest control rules inside the simulation, and this one.

This model works outside the simulation loop, as a helper that summarises and explains model runs, tables, charts and policy results; it does not take part in the simulation itself. In SURIMI a policy choice is a management strategy (a harvest control rule, a quota, a subsidy or an effort limit) tested by simulation across the ensemble (D3.1 to D3.8).

The model sits on the model GUI side of the platform, where what-if scenarios and policy measures live, with D3.7 on the data GUI side. It tells a user what simulations exist, explains their parameters, helps choose or compare scenarios, explains what-if results and trade-offs, and answers "what can this tool do?", while it does not write to storage or read data the user supplies. Like D3.7 it is built as a tool server, and the language model that drives it is replaceable.

The stock results it reads come from CMSY++, which estimates biomass and fishing pressure relative to maximum sustainable yield from catch and, where available, an abundance index ([Froese et al., 2017](https://doi.org/10.1111/faf.12190); [Froese et al., 2023](https://doi.org/10.3897/aiep.53.105910)). The gridded results are NetCDF files ([Rew and Davis, 1990](https://doi.org/10.1109/38.56302)), which the server reads with xarray ([Hoyer and Hamman, 2017](https://doi.org/10.5334/jors.148)).

### What SURIMI built and what it reuses

The server reuses the result format the CMSY++ script writes, NetCDF and xarray for the gridded files, the Model Context Protocol ([Anthropic, 2025](https://modelcontextprotocol.io/specification/2025-06-18)) and the chat stack of D3.7. Built for SURIMI:

- the model server and its 26 tools ([`surimi_model_mcp/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp));
- readers that report a stock's status per phase, with its bounds and estimator, by the rules of the CMSY++ script (section 4.2);
- pre-aggregated slices over gridded files, so that the language model never handles raw grid cells (section 4.3);
- the register of what the runs and files cannot answer (section 4.4).

## 3. Inputs

The user provides a single input, a policy question in natural language, and everything else the model reads sits in the bucket. The tools that read it are listed in Table 1.

### 3.1 Simulation runs

The runs are per-model bundles in the layout of Table 2, and the seven simulation tools of Table 1 read them, from the listing with its one-line summary and assessed stock per run, through one run's artifacts and parsed metadata, to the Kobe status and the year-indexed trajectory of a stock out of its CMSY++ result table or out of the run's NetCDF, and the meaning of any CMSY++ input or result column. The readers are in [`simulations/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/simulations).

The runs that the output creator writes carry the CMSY++ result as arrays inside the NetCDF file, not as a result table, and `model_run_stock_status` reads those: B/Bmsy and F/Fmsy for each stock, and with a stock named its trajectory and Kobe position. When the evaluation was run the bucket held one such run, with 47 western Mediterranean stocks up to 2013; on 12 October 2026 it held eight. The file has no uncertainty bounds and does not mark which years are historical and which simulated, and the tool says so in every response. The harvest-control-rule runs of the fisheries authority model, 35 when the evaluation was run and 54 on 12 October 2026, are served as artifacts through `model_get_artifact`.

The output file of an experiment is written by the Output Creator after the experiment ends, as one NetCDF4 file under `output_creator/experiments/<id>/`. It holds biomass, gross catch and live and dead discards on the model grid by species and fleet, with their totals per species and fleet. It also holds prices, sales value and sales quantity by market, and fishing activity by fleet. When the experiment includes stock assessments it adds stock status and exploitation by year and species, which `model_run_stock_status` reads. The value chain model is not finished, so no output file carries value-chain results yet.

### 3.2 Gridded forcing and observations

The files under `netcdf/` are external forcing and observation datasets on the same grid conventions as the ensemble, and the thirteen gridded tools of Table 1 return pre-aggregated, pivotable slices over them, so that raw grid cardinality never reaches the language model ([`netcdf/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/netcdf)).

### 3.3 Reference and contract

The reference tools of Table 1 name the ecosystem model behind a run, return the SURIMI scenario contract, and resolve species and gear codes, while `describe_model_capabilities` states which classes of question this server serves and which it does not ([`reference/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/reference)).

## 4. Outputs

### 4.1 Run discovery

A list of the SURIMI runs that bear on the question, each with the model, the scenario, the stock and the year range, flagged when the listing is stale or partial (Table 2).

### 4.2 Stock status and trajectory

The status of a stock in a given run and phase, as B/Bmsy and F/Fmsy with the bounds and estimator set out in Table 3, and its trajectory over the years. The answer names the source file.

A run is read the way the CMSY++ script wrote it.

*Table 3. How a stock result is read.*

| Setting | Value |
| --- | --- |
| Source | the CMSY++ result table of a run (`Out_..._id_file.csv`) |
| Phase | required argument, `historical` (assessed from observed catch and abundance) or `simulation` (assessed from ecosystem-model output); a run without that split is refused by file name |
| Estimator | reported per run, CMSY (catch only) or BSM (catch plus abundance index), decided by the same rule the CMSY++ script uses |
| Bounds | every point estimate carries `lcl` and `ucl`, stated as the 2.5th and 97.5th percentile of the MCMC posterior and not as a confidence interval |

### 4.3 Gridded slice and explanation

A series, trend, period comparison or ranking over named regions, with the file, variable and mask it came from, and a definition of any assessment field, code or contract element the user names, taken from the CMSY++ documentation, the SURIMI protocol or the reference tables.

### 4.4 Record and refusal

The five gridded analysis tools (`model_validate_alignment`, `model_top_regions`, `model_time_series`, `model_compare_periods` and `model_trend`) return a signed record (HMAC; [Krawczyk et al., 1997](https://doi.org/10.17487/RFC2104); [`provenance/`](https://github.com/SURIMI-Project/SURIMI-model-mcp/tree/master/surimi_model_mcp/provenance)) of the file, mask and parameters they used, and `model_verify` confirms that the record is unchanged. Run and stock results are not signed: they name the run, stock, phase and file they were read from. The model server reads files, not a database, so there is no query to re-run. Where no run or file supports the question this server's capability registry ([`sources.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/sources.py), [`capabilities.py`](https://github.com/SURIMI-Project/SURIMI-model-mcp/blob/master/surimi_model_mcp/capabilities.py)) says so and the answer states what was looked for.

## 5. Benchmark accuracy

D3.7, section 5, measures how often the deployed setup misreads a question or states an unsupported figure; this section reports the same for the policy questions. On this server two kinds of prompt steer the model: the tool descriptions the language model reads before each call and the system prompt of the ready to use wiring. Together they aim for one behaviour: the model answers only from SURIMI's runs and files and refuses what they do not support.

### 5.1 Objectives for each prompt

| Prompt | Objective |
| --- | --- |
| `model_list_simulations` description | Call first for any question about a run. Answer "which models have runs" from the scanned list, and "what is run X about" from the run's own summary and stock, without opening every run. Treat a null summary as unknown, never as a guess. Say when the listing is stale or partial. |
| `model_describe_simulation` description | Open one run only after the listing has picked it. Report artifacts and parsed metadata. |
| `model_get_stock_status` and `model_get_stock_trajectory` descriptions | Require the phase, historical or simulation, and refuse a run that has no such split, naming the file to fetch instead. Report every estimate with its bounds and say what the bounds are. Name the estimator, CMSY or BSM, and why. |
| `model_get_artifact` description | Fetch one file and say when the content is a cut prefix, never present it as the whole file. |
| `model_explain_assessment_field` description | Define a CMSY++ input or result column and how the script uses it, from the script's own documentation. |
| Gridded tool descriptions | Find the file, then the variable, then the exact region name from the mask, then call one analytic tool. Never guess a region name. Answer from the pre-aggregated summary. Prefer `model_trend` for "is it increasing" questions. |
| System prompt of the wiring, gridded workflow block | The same four-step order, stated once for every client that uses the shared prompt. |
| System prompt of the wiring, register and rules blocks | Lead with the answer in everyday words for policy-makers and stakeholders. Define terms at first use. Never invent a run, stock, file or number. State every figure plainly, naming the run, stock, phase and file. End every turn with a plain answer. |

### 5.2 How the model is evaluated

The first evaluation is its own behavioural benchmark of 33 cases, kept in the project's internal repository, each with a grounding command that recomputes the expected figure from the files and scored by the same deterministic grader as D3.7, which runs against every release.

The second is the expert evaluation described in D3.7, section 5.2. Three of the ten reviewers asked from a policy position: the fisheries economist E1 on the marine spatial planning form, the marine science policy adviser E2 and the science policy officer E10. Their 19 questions form the policy-facing subset, reported next to the figures for all 60.

### 5.4 Known limits

The model does not act inside the simulation: it does not read the state of the simulated fishery or emit regulations through the SURIMI protocol, and every answer about a scenario is an answer about a run that a modeller has already completed and uploaded.

The runs observed live carry one unlabelled CMSY++ result table and no historical or simulation split, so `model_get_stock_status` and `model_get_stock_trajectory` refuse them by name. Since model-mcp 1.2.8 the output runs are read from their NetCDF instead (section 3.1). In the same way, the bucket holds per-model run bundles named by scenario directory, not a catalogue of pre-run scenarios with a region, a climate scenario, a policy measure and a duration for each. When runs arrive in that shape, discovery works over them without a code change. The output run is on the model's own grid, 82 by 109 cells for the western Mediterranean, and no region mask on that grid is served, so a question about which areas a result applies to cannot be split by area with the tools.

The policy-facing subset is 19 questions, and the count answered moved by up to four between runs. All the questions declined although answerable are data-server questions.
