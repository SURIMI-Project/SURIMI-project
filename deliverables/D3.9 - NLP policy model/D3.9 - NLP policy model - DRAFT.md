## Summary

D3.9 answers policy questions about SURIMI in ordinary language: what a closure would do to
a fleet, how catches move under a scenario, which stocks a harvest control rule puts at
risk.

It shares its servers, its chat and its evaluation with D3.7. The difference is the kind of
question, and that difference is where it currently stands or falls.

Thirteen of the 68 expert questions ask for a scenario, a counterfactual or a forward
projection. None is answered today. Six are questions SURIMI could answer if the run
existed, and no client has answered any of them. The other seven are correctly refused,
because SURIMI holds no output to answer them from.

The interface is built and the reasoning works. What is missing is scenario output to read.

## 1. Model purpose

D3.9 takes a policy question in plain language and answers it from SURIMI's scenario
output: what changes between runs, which fleets or stocks are affected, and by how much.

The intended user is a manager or adviser who wants to compare options, not a modeller who
can open a NetCDF file.

The model does not run simulations. It reads runs that already exist. A question that
requires a run nobody has performed is refused, with the reason stated.

## 2. Inputs

The user gives the model one input: a policy question in natural language.

The model reads the same published sources as D3.7, and one more that matters here:

- **Scenario output.** Gridded model results per run, with the species, fleet and time
  axes needed to compare one scenario against another.
- **Tabular observations**, for the historical baseline a scenario is judged against.
- **Documentation**, for what a scenario, a fleet segment or a control rule means.

At the time of writing, one model run is listed on the model server. It carries no scenario
description and no comparison case, so a question of the form "what changes if" has nothing
to read.

## 3. Outputs

- An answer in plain language, naming the run it came from.
- A comparison between runs, where more than one exists.
- A refusal with a stated reason, where no run supports the question.
- The same public audit page as D3.7, carrying every evaluation question with its answer
  and sources.

## 4. Objectives

The model should answer a policy question from scenario output that exists, refuse one that
needs a run nobody has performed, and never present a projection it cannot support.

### 4.1 How the model is evaluated

The method is D3.7's, and section 4.1 of that deliverable describes it. Eleven domain
experts filed fifteen survey submissions, ten contributed questions, and we established
each expected answer from the raw data before testing.

Thirteen of the 68 questions are policy questions, and the figures below are those
thirteen.

### 4.3 Known limits

The limit is the absence of scenario output, not the language model. Five of the six
unanswered questions need a simulation SURIMI has not run, and no cataloguing work reaches
them. The sixth needs an optimiser, which nothing in the stack provides.

Q-E3-7 asks for a protection strategy. Answering it requires an objective function and a
solver, which is a modelling decision for the consortium and not a gap in this module.

The strongest client measured reaches none of the six either, so this is not the chat model
choosing badly.

The evaluation set is not tagged by deliverable. The thirteen policy questions were
identified by reading all 68, and a reviewer may draw the line in a different place.
